Ley Visual y Ley Lote intercambiadas en mezclas importadas (Catemu insoluble/soluble)

Bug
Módulo Dispatch — Mezclas · Producción y BD local · Detectado comparando mezcla EN188 contra el Excel real

Problema

En la vista de una mezcla, la columna "Ley Lote" salía igual para todos los componentes (ej. 1.50% en las 9 filas de la mezcla EN188), cuando debería variar por dumpada porque se calcula desde el laboratorio. La columna "Ley Visual" en cambio sí variaba fila a fila, cuando en la realidad la ley visual es un estimado a ojo que se asigna igual para todo un frente/turno (por eso debería ser la que sale constante). Los totales de la mezcla tampoco calzaban con el Excel de origen que usa el laboratorio para llevar el control paralelo.

Guardado en BD (antes) Ley Visual: 1.26%, 0.75%, 1.52%... (varía)
Ley Lote: 1.50% en las 9 filas (constante)
Total Ley Lab mostrado: 1.85%
Excel real (columnas N y O) LEY VISUAL: 1.50% en las 9 filas (constante)
LEY LOTE Insoluble: 1.26%, 0.75%, 1.51%... (varía)
Fila "Ley Lab" del Excel: 1.42%

Causa

Se abrió el Excel real del usuario (Planilla Julio InsolubleCatemu.xlsx, hoja "Mezcla") con un script de Node usando la librería xlsx para ver el orden exacto de columnas en la cabecera de la mezcla EN188 (fila 4207): L=LEY DUMP insoluble, M=LEY DUMP Soluble, N=LEY VISUAL, O=LEY LOTE Insoluble, P=LEY LOTE Soluble.

En ImportarMezclasView.jsx, función detectarMapeoLeyes(), el mapeo de columnas para el formato Catemu tenía "Ley Visual" y "Ley Lote" invertidas:

// ANTES (columnas 13 y 14 cruzadas)
if (sumInsol >= sumSol) {
  return { ley_dump: 11, ley_lote: 13, ley_visual: 14, formato: 'catemu-insoluble' };
} else {
  return { ley_dump: 12, ley_lote: 13, ley_visual: 15, formato: 'catemu-soluble' };
}

// DESPUÉS
if (sumInsol >= sumSol) {
  return { ley_dump: 11, ley_visual: 13, ley_lote: 14, formato: 'catemu-insoluble' };
} else {
  return { ley_dump: 12, ley_visual: 13, ley_lote: 15, formato: 'catemu-soluble' };
}

El importador (ImportarMezclasController::confirmar, backend) copia estos valores tal cual del Excel a las columnas ley_visual/ley_lote de mezcla_dumpada, así que el swap de columnas en el frontend se propagaba directo a la base de datos. El bug no afectaba mezclas armadas manualmente con "Agregar Dumpadas" (esas usan MezclaDumpada::desdeDumpada(), que sí calcula bien lab×0.9 / lab×0.81).

Solución

  • Se corrigió el mapeo de columnas en detectarMapeoLeyes() para las próximas importaciones.
  • Se creó la migración 2026_07_24_000001_fix_mezcla_dumpada_visual_lote_swap.php, que:
    1. Detecta filas de mezcla_dumpada donde ley_visual calza (con tolerancia de ±0.01, por redondeos previos) con el valor que debería tener ley_lote según la ley de laboratorio real de la dumpada (cu_insoluble/cu_soluble/ley según el ley_base de la mezcla, con capping y ×0.81).
    2. Intercambia ley_visual ↔ ley_lote en esas filas (no se pierde información, solo estaba en la columna equivocada).
    3. Recalcula los promedios de cada mezcla afectada con Mezcla::calcularTotales(), el mismo método que ya usa el resto del sistema.

Probado primero en BD local (copia de producción, 2026-07-24): 1.292 filas corregidas en 198 mezclas (dos pasadas: 1.154 filas / 105 mezclas en la primera detección exacta, 138 filas / 93 mezclas adicionales tras ajustar la tolerancia de redondeo). Verificación en EN188: Ley Dump 1.28%, Ley Lote 1.15%, Ley Lab 1.42% — los tres calzan exacto con el Excel de origen.

Código de dumpadas importadas desde Excel no incluía el número de jornada

Bug
Módulo Dispatch / Laboratorio · Producción y BD local

Problema

En el listado de dumpadas, las creadas manualmente mostraban un código bien formado (ej. NIVEL975 AM 4 3328 24.07.2026), pero las que venían de una importación de Excel salían sin el número de jornada y con la fecha en otro formato (ej. NIVEL 974 M4 6N L33 AM 3323 16-07-2026). El campo "Jornada" de la tabla sí mostraba el número correcto (se lee en vivo desde la base de datos), lo que hacía parecer que el problema era la numeración cuando en realidad era solo el texto guardado.

Importado (antes) NIVEL 974 M4 6N L33 AM 3323 16-07-2026
Manual / esperado NIVEL974M46NL33 AM 2 3323 16.07.2026

Causa

El ingreso manual (DumpadaController::store) arma el campo acopios (el "Código" que se muestra) combinando frente + jornada + número de jornada + número de dumpada + fecha. El importador (ImportarDumpadasController::confirmar) en cambio copiaba tal cual el texto que traía la columna "acopios" del Excel de origen, sin reconstruirlo con el número de jornada calculado por el sistema.

Solución

  • Se corrigió ImportarDumpadasController.php para que arme el código igual que el ingreso manual.
  • Se corrieron ~9.650 registros existentes con un UPDATE que regeneró el campo acopios usando los datos ya correctos en base de datos (frente, jornada, número de jornada, número de dumpada, fecha). No tocó numeración ni ningún otro campo.
UPDATE dumpadas d
JOIN frentes_trabajo ft ON ft.id = d.id_frente_trabajo
SET d.acopios = TRIM(CONCAT(
  ft.codigo_completo, ' ', d.jornada, ' ', d.numero_jornada, ' ', d.numero_dumpada, ' ', DATE_FORMAT(d.fecha, '%d.%m.%Y')
))
WHERE d.acopios != TRIM(CONCAT(
  ft.codigo_completo, ' ', d.jornada, ' ', d.numero_jornada, ' ', d.numero_dumpada, ' ', DATE_FORMAT(d.fecha, '%d.%m.%Y')
));

Error 500 al completar análisis de laboratorio (columna faltante)

Bug
Módulo Laboratorio · Producción

Problema

POST /api/laboratorio/dumpadas/completar-multiples devolvía error 500 al intentar completar análisis de laboratorio en producción.

Causa

La migración 2026_07_21_000001_add_fecha_analisis_completado_to_dumpadas_table.php (que agrega la columna fecha_analisis_completado a dumpadas) se subió con el código pero nunca se corrió en el servidor de producción. El controlador intentaba guardar esa columna y MySQL respondía "Unknown column".

Solución

Se corrió la migración pendiente en el servidor, usando el binario de PHP 8.2 (el php del PATH por defecto resuelve a 8.1.34, que no cumple el mínimo del proyecto):

/opt/cpanel/ea-php82/root/usr/bin/php artisan migrate --force

Integración con Sistema de Petróleo rota tras config:cache

Fix
Módulo Dispatch (camiones tolva) · Producción

Problema

El endpoint de camiones tolva (PetroleController::maquinas) dejaba de encontrar la URL del Sistema de Petróleo en producción.

Causa

env('SISTEMA_PETROLEO_API') se usaba directo en el controlador. env() deja de funcionar fuera de archivos de configuración después de correr config:cache (que el deploy de este repo ejecuta), devolviendo null.

Solución

Se reemplazó por config('services.petroleo_api'), que ya existía definido en config/services.php pero no se estaba usando.
