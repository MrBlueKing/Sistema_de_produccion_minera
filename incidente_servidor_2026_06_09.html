Servidor HostingPlus — mhcl — 45.239.111.148

RESUELTO

Resumen Ejecutivo

El servidor sufrió caídas intermitentes durante varias horas debido a un ataque de fuerza bruta sostenido contra los archivos xmlrpc.php de múltiples instalaciones WordPress alojadas en el mismo servidor. Este ataque agotó la memoria RAM disponible para PHP-FPM, dejando sin respuesta a Apache y, por cascada, a todos los sistemas (petroleo.m3h.cl, produccion.m3h.cl, auth-api.m3h.cl).

El incidente fue identificado, contenido y resuelto. Se aplicaron medidas de seguridad permanentes en todos los sitios WordPress afectados.

Causa Raíz del Incidente

Ataque de fuerza bruta WordPress (xmlrpc.php)

El archivo xmlrpc.php es una interfaz XML-RPC de WordPress que permite ejecutar comandos de forma remota. Atacantes la usaron para lanzar miles de peticiones simultáneas intentando adivinar credenciales de administrador.

Cada petición levantaba un worker de PHP-FPM consumiendo ~780 MB de memoria virtual. Con suficientes peticiones concurrentes, la RAM del servidor se agotó y Apache dejó de responder completamente — incluyendo todos los sistemas Laravel del servidor.

Cadena de fallo:
Ataque xmlrpc.php → PHP-FPM workers llenos → RAM agotada → Apache sin respuesta → auth-api.m3h.cl timeout → produccion.m3h.cl y petroleo.m3h.cl sin autenticación

También se detectó actividad de un escáner de vulnerabilidades desde la IP 172.202.96.198 intentando acceder a archivos de webshells (/wp-content/plugins/xmlrpc.php, etc.).

Contención inmediata

Mitigación permanente
Se bloquea xmlrpc.php y wp-login.php en los 5 sitios WordPress del servidor via .htaccess.
Problema secundario — api.m3h.cl
Sistema de petróleo sin conexión. Causa: api.m3h.cl estaba en PHP 8.0 pero el código requiere PHP 8.2.
Fix api.m3h.cl
Actualizado PHP de api.m3h.cl a 8.2 en MultiPHP Manager. Sistema de petróleo restaurado.
Problema secundario — m3h.cl
WP Toolkit actualizó WordPress a 7.0 pero PHP seguía en 7.3 → Error 500. Actualizado PHP a 8.1 pero persiste error fatal por plugin incompatible.
Fix m3h.cl
Plugin anwp-post-grid-for-elementor deshabilitado (usaba clase Elementor eliminada). m3h.cl restaurado. WP_DEBUG desactivado.

Acciones Realizadas

1. Bloqueo de xmlrpc.php en todos los WordPress

Se agregó en el .htaccess de cada instalación:

<Files xmlrpc.php>
Order Deny,Allow
Deny from all
</Files>

<Files wp-login.php>
Order Deny,Allow
Deny from all
Allow from TU_IP_OFICINA
</Files>

Sitios protegidos:

  • /home/mhcl/public_html/.htaccess — m3h.cl (raíz, daar.cl apunta aquí)
  • /home/mhcl/public_html/daar.cl/.htaccess
  • /home/mhcl/public_html/neumaticos.daar.cl/.htaccess
  • /home/mhcl/public_html/container.daar.cl/.htaccess
  • /home/mhcl/public_html/autoevaluacion/.htaccess
  • /home/mhcl/public_html/wp/.htaccess

2. Bloqueo de IP escáner en CSF

IP 172.202.96.198 bloqueada en WHM → Plugins → ConfigServer Security & Firewall.

3. Aplicación de medidas de seguridad WP Toolkit

Se aplicaron las hardening measures de WP Toolkit en los 6 sitios WordPress.

5. Fix plugin incompatible en m3h.cl

Plugin anwp-post-grid-for-elementor deshabilitado renombrando su carpeta:

mv /home/mhcl/public_html/wp-content/plugins/anwp-post-grid-for-elementor \
   /home/mhcl/public_html/wp-content/plugins/anwp-post-grid-for-elementor.disabled

Causa: WP Toolkit actualizó Elementor y eliminó la clase Elementor\Core\Schemes\Typography que el plugin requería.

6. WP_DEBUG desactivado en m3h.cl

sed -i "s/define( 'WP_DEBUG', true )/define( 'WP_DEBUG', false )/" \
    /home/mhcl/public_html/wp-config.php

Lecciones Aprendidas

  • xmlrpc.php debe bloquearse por defecto en todos los WordPress que no usen XML-RPC (casi ninguno lo necesita hoy en día).
  • WordPress en un servidor compartido con sistemas críticos es un riesgo. Un ataque a WordPress puede derribar toda la infraestructura por agotamiento de recursos.
  • WP Toolkit actualiza WordPress automáticamente sin verificar compatibilidad de plugins — esto rompió m3h.cl.
  • Las versiones de PHP deben auditarse periódicamente — api.m3h.cl llevaba tiempo en PHP 8.0 sin detectarse.
  • El monitoreo externo es esencial — el incidente fue detectado por el usuario intentando usar el sistema, no por una alerta automática.
