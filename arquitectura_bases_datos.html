1. Integridad de los Datos — Fundamento del Sistema

La integridad de los datos es la garantía de que la información almacenada en el sistema es exacta, consistente y confiable en todo momento. Para una operación minera, esto es crítico: una ley de cobre incorrecta, una camionada mal registrada o un análisis de laboratorio modificado sin autorización puede tener consecuencias económicas y legales directas.

La integridad de los datos no es opcional. Un sistema que no la garantiza no puede usarse como fuente confiable para toma de decisiones, auditorías ni compromisos comerciales. Todos los controles de seguridad descritos en este documento tienen como objetivo final proteger esta integridad.

1.1 Niveles de Integridad de Datos

La teoría de bases de datos define cuatro niveles de integridad, cada uno protegiendo un aspecto distinto:

Integridad de Entidad

Cada registro debe tener un identificador único y no nulo (Primary Key). Garantiza que no existan dos dumpadas con el mismo número, dos mezclas con el mismo código o dos camionadas idénticas.

En el sistema: implementado mediante claves primarias autoincrementales en todas las tablas.

Integridad Referencial

Las relaciones entre tablas deben ser válidas (Foreign Keys). Una camionada siempre debe pertenecer a una mezcla que existe; un análisis siempre debe estar asociado a una dumpada real.

En el sistema: implementado con claves foráneas entre dumpadas, mezclas, lotes y camionadas.

Integridad de Dominio

Los valores deben estar dentro de rangos y tipos válidos. Un porcentaje de Cu Total no puede ser negativo ni mayor a 100%; una jornada solo puede ser AM o PM; el tonelaje debe ser positivo.

En el sistema: implementado mediante validaciones en el backend Laravel antes de insertar cualquier dato.

Integridad de Usuario

Reglas de negocio específicas de la operación. Una mezcla no puede tener más toneladas despachadas que su tonelaje total; un lote cerrado no puede recibir nuevas camionadas.

En el sistema: implementado con validaciones de lógica de negocio en los controladores de la API.

1.2 Tríada CIA — Los Tres Pilares de la Seguridad de Datos

Desde el punto de vista de seguridad informática, proteger los datos implica garantizar tres propiedades simultáneamente. Cada mejora propuesta en este documento está vinculada a uno o más de estos pilares:

C

Confidencialidad

Solo las personas autorizadas pueden acceder a los datos. Un usuario de Catemu no puede ver datos de Cabildo. Un operador de Dispatch no puede acceder a datos de otra empresa ni de otra faena.

I

Integridad

Los datos no pueden ser modificados sin autorización. Un resultado de laboratorio no puede ser alterado por Dispatch. Una ley de venta no puede cambiar después del cierre de un lote.

A

Disponibilidad

Los datos deben estar accesibles cuando se necesitan. Si el sistema cae durante un turno de despacho, la operación se paraliza. Los backups y el monitoreo protegen esta propiedad.

2. Infraestructura y Servidor de Alojamiento

Todos los sistemas M3H están alojados en un servidor centralizado administrado por HostingPlus (Chile). Los datos no se almacenan en los equipos de la faena: todo acceso ocurre a través del navegador web mediante conexión cifrada HTTPS. Si un equipo de faena se daña o pierde, los datos permanecen intactos en el servidor.

6. Respuestas a las Preguntas de Dirección

1 ¿La base de datos es única o son varias?
Son múltiples bases de datos independientes. Existen 3 bases de datos propias de los sistemas M3H, alojadas en el mismo servidor pero completamente separadas. Ningún sistema accede directamente a la base de datos de otro.

mhcl_sistema_produccion — Dispatch, Laboratorio, Ingeniería, Abastecimiento
mhcl_gestion_petroleo — Gestión de Petróleo
mhcl_sistema_autenticacion — Usuarios, roles y sesiones de todos los sistemas
2 ¿Dónde están alojadas las bases de datos?
En un servidor físico de HostingPlus (empresa chilena), IP 45.239.111.148, administrado mediante cPanel bajo el usuario mhcl. Los datos no se almacenan en los equipos de la faena. Todo acceso es vía navegador web con HTTPS. Si un equipo de faena se daña o pierde, los datos permanecen intactos.
3 ¿El Laboratorio maneja su propia base de datos?
No. El Laboratorio trabaja sobre la misma base de datos del Sistema de Producción (mhcl_sistema_produccion), pero con un rol restringido: el Analista de Laboratorio solo puede ingresar y modificar resultados de análisis (Cu Total, Cu Soluble) y generar certificados. No puede modificar dumpadas, mezclas ni despachos.

Esta decisión de diseño garantiza que cuando el Laboratorio ingresa una ley, Dispatch la ve de inmediato, sin necesidad de exportar ni enviar archivos.
4 ¿Puede otra área ver o modificar los datos del Laboratorio?
Ver: sí, los resultados del análisis son visibles para Dispatch (los necesita para calcular las leyes de las mezclas).
Modificar: solo el Analista de Laboratorio puede ingresar y editar resultados de análisis. Dispatch no puede alterarlos.
5 ¿Se hacen backups? ¿Con qué frecuencia?
Sí. HostingPlus realiza backups automáticos semanales, los días domingo. El último registrado fue el 21 de junio de 2026. Incluye todas las bases de datos y archivos del servidor.

Riesgo identificado: al ser semanal, en el peor escenario se podrían perder hasta 6 días de datos operacionales. No existen backups diarios ni copia externa fuera del servidor actualmente.

7. Mejoras Propuestas

Las siguientes mejoras están ordenadas por prioridad. Cada una indica qué pilar de la tríada CIA protege.

1
Prioridad alta

Backup diario automático de las bases de datos

Configurar un cron job en el servidor que exporte las tres bases de datos M3H cada noche a las 2:00 AM. Con el backup semanal actual se pueden perder hasta 6 días de registros de dumpadas, análisis de laboratorio y despachos. Un backup diario reduce ese riesgo a máximo 24 horas. El costo es prácticamente cero.

Prioridad alta

Backup externo fuera del servidor

Además del backup semanal de HostingPlus, enviar automáticamente una copia del SQL a un almacenamiento externo: Google Drive, OneDrive o un PC designado en la oficina central. Si el servidor físico de HostingPlus falla completamente, la copia no está en el mismo lugar que el problema. Hoy el backup y los datos viven en el mismo servidor.

Disponibilidad
3
Prioridad alta

Revisar y limitar permisos del usuario mhcl_root

Se identificó un usuario de base de datos llamado mhcl_root. Los usuarios suelen crearse con "ALL PRIVILEGES", lo que permite borrar tablas o acceder a cualquier base de datos del servidor. La práctica correcta es otorgar a cada usuario solo los permisos mínimos necesarios para su función: SELECT, INSERT, UPDATE y DELETE — nunca DROP ni CREATE en producción, y nunca con acceso a bases de datos de otros sistemas.

ConfidencialidadIntegridad
4
Prioridad alta

Aislar o eliminar los sitios WordPress del servidor

Los tres sitios WordPress (wp147, wp366, wp588) comparten servidor con todos los datos operacionales de la mina. WordPress es el CMS más atacado del mundo debido a la proliferación de plugins vulnerables y versiones desactualizadas. Un ataque exitoso a cualquiera de estos sitios puede comprometer la disponibilidad y la integridad de todas las bases de datos que conviven en el mismo servidor. Lo ideal es moverlos a un hosting separado o eliminarlos si no se usan activamente.

5
Prioridad media

Protección contra ataques de fuerza bruta al login

Actualmente el sistema no tiene límite de intentos de inicio de sesión fallidos. Un atacante podría probar miles de combinaciones usuario/contraseña de forma automatizada. Implementar un bloqueo temporal después de N intentos fallidos (por ejemplo, 5 intentos en 10 minutos) protege directamente la confidencialidad de los datos: si nadie puede entrar sin autorización, nadie puede ver ni modificar análisis de laboratorio, leyes ni despachos.

Log de auditoría para datos críticos

Registrar automáticamente cada modificación a un análisis de laboratorio, una ley, un certificado o un despacho: usuario que lo modificó, fecha y hora, valor anterior y valor nuevo. Permite demostrar la integridad de los datos ante cualquier disputa sobre un resultado o certificado. Es la evidencia formal de que los datos no fueron alterados.

Rotación periódica de contraseñas

Aplica en dos niveles. Usuarios del sistema (Dispatch, Laboratorio, etc.): expiración obligatoria de contraseña cada 90 días — si una contraseña es robada, su vida útil es limitada. Usuarios de base de datos (mhcl_sistema_produccion, etc.): rotar sus contraseñas periódicamente y actualizar los archivos de configuración del servidor. Práctica estándar en grandes empresas para reducir el impacto de una filtración de credenciales.

Documentar y probar el procedimiento de recuperación

Existe un backup semanal, pero no hay un procedimiento documentado de cómo restaurarlo ni cuánto tiempo toma. Se recomienda realizar al menos una vez al año una restauración de prueba en un entorno de desarrollo, para verificar que los datos son recuperables y que el equipo sabe cómo hacerlo antes de que ocurra una emergencia real.
